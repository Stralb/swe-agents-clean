## Release and isolation boundaries

1. Gitleaks uses a fixed harmless synthetic Gitleaks TOML rule. Semgrep uses one fixed harmless Python rule. Neither rule is represented as the historic vulnerability methodology.
2. The Semgrep sandbox is built with network access, but its **test container** runs with Docker `--network none`, a non-root UID/GID, read-only root+worktree, a limited disposable `/tmp`, dropped Linux capabilities, `no-new-privileges`, and process/memory caps. The initial offline `semgrep --version` call hung until the environment set **`SEMGREP_ENABLE_VERSION_CHECK=0`**, then the unchanged tests passed. This remains a candidate setup for real-repo sandbox hardening, not authorization to scan unknown repositories.
3. The pinned Gitleaks release archive and Semgrep top-level wheel do not identify the *historically deployed* tool versions. The Semgrep image base tag and transitive pip dependencies are not immutable; the workflow logs `pip freeze` and image identifier for debugging only. No full dependency SBOM has been independently audited.
4. Exact historical dependency parsing and OSV/Trivy pure attribution checks expose possible false positives, missing-alias matches and conflicting status precedence. These are original code mechanisms only; prevalence is unknown. The original `_clear_scanner` cross-scanner deletion by finding type, status handling for `not_applicable` and `code_quality`, error-run caching, and D/D7 disagreement are **known, unchanged historical behavior**. Reproducing them in tests does not show how frequently they affected actual data.
5. No original Wits research files, Slurm jobs, original study repos, or production scanner databases were accessed or changed in this milestone. Never merge PR #1 solely because synthetic or real-executable smoke tests pass.
